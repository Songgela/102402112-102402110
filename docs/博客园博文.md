## 3. 解题思路描述与设计实现说明

### 3.1 总体思路

作业要求打通这条主流程：

> **发布信息 → 浏览或搜索 → 查看详情 → 联系发布者 → 更新状态**

我们二人围绕这条主线做设计，核心决策有三个：

**决策一：为什么选择纯静态 Web（原生 HTML/CSS/JS），而不是框架？**

作业明确要求「**确保其他同学在下载你的所有文件后，用谷歌浏览器运行 HTML 文件就能展现预期结果**」。
如果用 React/Vue，助教需要装 Node、跑 `npm install`、启动 dev server，任何一步出问题都会
导致「跑不起来」而丢便捷性分数。因此我们选择：

- 原生 HTML + CSS + JavaScript，**零框架、零构建、零依赖**
- 数据存储用 `localStorage`，无需后端服务
- 单元测试框架 Mocha/Chai 也**下载为本地文件**，保证断网也能运行测试

这个决策的收益在测试环节非常明显：助教双击 `index.html` 就能看到完整的带数据界面。

**决策二：三层架构分离**

为了让 `store.js` 可被单元测试直接测试，我们把业务逻辑与 DOM 操作彻底解耦：

| 层级 | 文件 | 职责 | 是否碰 DOM |
|---|---|---|---|
| 数据层 | `store.js` | 搜索、筛选、校验、统计、状态流转 | ❌ 完全不碰 |
| 数据层 | `data.js` | 常量与示例数据 | ❌ |
| 视图层 | `views.js` | 数据 → HTML 字符串 | ❌（只拼字符串） |
| 入口层 | `app.js` | 路由、事件绑定、编排 | ✔ 唯一操作 DOM 的地方 |

这样做的直接好处：**61 个单元测试可以直接 `require('../js/store.js')` 断言，
不需要 jsdom、不需要启动浏览器**。这正是分层带来的可测试性红利。

**决策三：状态流转采用「不可变更新」**

`updateStatus(items, id, status)` 不修改传入数组，而是返回新数组（内部用 `map` 生成新对象）。
这样做的原因：视图层可能在多处持有同一份数据引用，如果原地修改，容易产生「数据改了但界面没刷新」
或者「刷新了但引用了脏数据」的诡异问题。不可变更新的代价是内存开销略高，但对于校园级数据量完全可以接受。

### 3.4 重要的代码片段与解释

#### 片段 1：关键词搜索 + 多条件组合筛选（`store.js`）

```javascript
function searchItems(items, query) {
  var list = Array.isArray(items) ? items.slice() : [];
  if (!query) { return list; }

  var keyword = String(query.keyword || '').trim().toLowerCase();

  return list.filter(function (item) {
    if (keyword) {
      var haystack = [
        item.title || '',
        item.description || '',
        item.place || ''
      ].join(' ').toLowerCase();
      if (haystack.indexOf(keyword) === -1) { return false; }
    }
    if (query.type && item.type !== query.type) { return false; }
    if (query.category && item.category !== query.category) { return false; }
    if (query.status && item.status !== query.status) { return false; }
    return true;
  });
}
```

**为什么这么写？**

- `items.slice()` **先拷贝再操作**，保证函数是纯函数，不污染调用方数据。
  这是本项目的统一约定，单元测试「用例 15」专门验证了这一点。
- **三层字段拼成 haystack 再统一匹配**：用户搜「图书馆」可能想找「地点在图书馆的物品」，
  搜「校园卡」可能是物品名，搜「恐龙」可能是描述里的特征词。把标题、描述、地点合成一个
  搜索域，一次 `indexOf` 就能覆盖全部场景，比写三个 `||` 判断更简洁，也更容易扩展
  （将来要加「搜索联系人姓名」只需往数组里加一项）。
- `toLowerCase()` 统一转小写实现**大小写不敏感**搜索。「用例 4」用 `airpods` / `AIRPODS` /
  `AiRpOdS` 三种写法验证了这个特性。
- **筛选条件用「有值才判断」的短路写法**：`if (query.status && item.status !== query.status)`。
  这样调用方只需传关心的条件，其他留空即可，无需构造完整的 query 对象。

#### 片段 2：不可变的状态更新（`store.js`）

```javascript
function updateStatus(items, id, status) {
  var list = Array.isArray(items) ? items : [];
  return list.map(function (item) {
    if (item.id !== id) { return item; }
    var next = Object.assign({}, item);      // 浅拷贝，生成新对象
    next.status = status;
    next.statusUpdatedAt = status === STATUS.CLOSED ? new Date().toISOString() : null;
    return next;
  });
}
```

**为什么这么写？**

- 用 `map` 而非 `forEach` + 原地赋值：`map` 天然返回新数组，从函数签名就能看出
  「这是一个不可变更新」，调用方不会担心原数据被改。
- `Object.assign({}, item)` 生成新对象而非改原对象。项目里同一个 id 的记录可能同时被
  列表渲染函数和详情抽屉引用，原地修改会导致「改了列表，详情看着新了，但点开别的又串了」
  这类难排查的 bug。
- **回滚时把 `statusUpdatedAt` 置为 `null`**：因为「重新打开」意味着这条记录不再是
  已结束状态，统计「平均找回时长」时不应把它算进去。「用例 21」验证了这个回滚行为。

#### 片段 3：表单校验（`store.js`）—— 一次返回全部错误

```javascript
function validateItem(data) {
  var errors = {};
  if (!data || typeof data !== 'object') {
    return { valid: false, errors: { _global: '数据格式不正确' } };
  }

  if (!data.title || String(data.title).trim().length < 2) {
    errors.title = '物品名称至少需要 2 个字符';
  } else if (String(data.title).trim().length > 30) {
    errors.title = '物品名称不能超过 30 个字符';
  }
  // ... 其余字段同理 ...

  // 联系方式采用「二选一」策略：手机号或 IM 至少填一个
  var phoneOk = /^1[3-9]\d{9}$/.test(String(contact.phone || '').trim());
  var imOk = String(contact.im || '').trim().length >= 4;
  if (!phoneOk && !imOk) {
    errors.contact = '请至少填写一个有效的联系方式（11 位手机号，或 QQ / 微信号）';
  }

  var keys = Object.keys(errors);
  return { valid: keys.length === 0, errors: errors };
}
```

**为什么这么写？**

- **不提前 return，把所有错误一次性收集完再返回**。如果写成「发现第一个错误就返回」，
  用户要反复提交 5 次才能把 5 个字段的错误都填对，体验很差。现在一次提交就能把
  `title`、`category`、`date`、`contact` 等全部标红。「用例 31」专门验证了这个行为。
- **用 `errors` 对象的键对应表单字段名**，渲染层只需 `$('[data-error="' + key + '"]')`
  就能定位到错误提示容器，无需写一堆 if-else 映射。
- **手机号正则 `/^1[3-9]\d{9}$/`**：这是中国大陆手机号的常用校验规则（1 开头，
  第二位 3-9，共 11 位）。比只判断长度更严格，能拦住 `12345678901` 这类无效输入。
- **联系方式「二选一」**：考虑到学生可能只愿意留微信不留手机号，所以设计成
  「手机号有效 或 IM 长度 ≥ 4」满足其一即可。「用例 29」「用例 30」分别验证了
  两种路径。

#### 片段 4：事件委托（`app.js`）—— 一个监听器管全站

```javascript
document.addEventListener('click', function (e) {
  var navEl = e.target.closest('[data-nav]');
  var actEl = e.target.closest('[data-action]');
  var card  = e.target.closest('.item-card');
  var copyEl = e.target.closest('[data-copy]');

  // 优先级很重要：先判断更具体的目标
  if (navEl) { e.preventDefault(); go(navEl.getAttribute('data-nav')); return; }
  if (copyEl) { e.stopPropagation(); /* 复制逻辑 */ return; }
  if (actEl)  { e.stopPropagation(); /* 操作逻辑 */ return; }
  if (card)   { openDetail(card.getAttribute('data-id')); }
});
```

**为什么这么写？**

- **列表会频繁重渲染**（搜索、筛选、标记状态后都要重新生成卡片 HTML）。如果给每张卡片
  单独 `addEventListener`，每次重渲染都要重新绑定，既冗余又容易漏绑、重复绑。
  事件委托把监听器挂在整个 `document` 上，**不管列表怎么重渲染，事件永远有效**。
- **判断顺序体现优先级**：一张卡片里面可能同时包含「卡片本身」（data-id）和
  「卡片内的复制按钮」（data-copy）。必须先判断更具体的目标，否则点复制按钮会同时
  触发「打开详情」。`return` 语句保证了这一点。
- `closest()` 会向上查找祖先节点，所以用户点到卡片里的文字、图标、标签都能正确识别
  为「点了这张卡片」，不需要给每层子元素绑定事件。

#### 片段 5：剪贴板复制的降级方案（`app.js`）

```javascript
    navigator.clipboard.writeText(text)
      .then(function () { toast('已复制：' + text, 'success'); })
      .catch(fallback);          // 现代 API 失败时回退
  } else {
    fallback();                  // 不支持现代 API 时直接回退
  }
}
```

**为什么这么写？**

- `navigator.clipboard` 是较新的 API，**在 `file://` 协议下很多浏览器会拒绝授权**
  （因为不是安全上下文）。而本作业要求「双击 HTML 直接运行」，恰好就是 `file://` 场景。
  如果只用新 API，助教本地测试时会遇到「点了复制没反应」的问题。
- `document.execCommand('copy')` 虽然已标记为废弃，但在 `file://` 下仍广泛可用，
  作为兜底方案效果很好。
- **双层保险**：先试新 API，`.catch()` 到降级方案；如果浏览器连 `navigator.clipboard`
  都没有（老版本），直接走降级。这保证了在任何环境下复制功能都可用。

## 4. 附加特点设计与展示

### 4.1 附加特点一：一键复制联系方式 + 手机号脱敏保护

#### 设计的创意独到之处与意义

作业的评分规则里明确举例提到「**一键复制联系方式**」这个方向。我们在此基础上做了
一个额外思考：**直接明文展示手机号，等于把发布者的隐私暴露给所有访问页面的爬虫**。

因此我们的设计是：

| 状态 | 显示 | 用户操作 |
|---|---|---|
| 初始 | `138****5678`（脱敏） | 点击手机号 |
| 第一次点击 | `13812345678`（明文展开） | 再次点击 |
| 第二次点击 | 不变 | 自动复制到剪贴板 + Toast 提示 |

**这个设计的双重价值**：

1. **对发布者**：号码不会被自动化脚本批量抓取（很多失物招领页面会被人肉爬虫扫号码用于推销）；
2. **对使用者**：真正的联系动作只需两次点击，且复制后有明确的成功反馈——「已复制：13812345678」，
   避免用户不确定有没有复制成功而反复点击。

同时详情面板底部还有两个显式的大按钮「📋 一键复制手机号」「📋 一键复制微信号」，
给追求效率的用户一条更短的路径。

#### 实现思路

- 脱敏：`store.js` 的 `maskPhone()` 把 11 位手机号的第 4-7 位替换为 `****`，
  非手机号格式的输入原样返回（不会误截断短的 IM 号）。
- 展开状态用一个模块级变量 `phoneRevealed` 管理，点击手机号时先判断是否已展开，
  未展开则展开（并刷新抽屉），已展开则执行复制。
- 复制走 `copyText()`，内部有 `navigator.clipboard` → `execCommand` 的降级链（见 3.4 片段 5）。

### 4.2 附加特点二：数据统计看板（5 分）

#### 设计的创意独到之处与意义

作业不要求后台管理，但我们认为：**一个失物招领平台光有「列表」是没有生命力的**，
它应该能回答一个更有价值的问题——**「这个校园的失物找回情况到底怎么样？」**

因此我们增加了一个数据看板页面，它承担三个作用：

1. **对用户**：展示「找回率 40%」这类数字，传递「发了真的有用」的信任感，
   激励更多人来发布和归还；
2. **对校园管理者**：想优化失物招领工作（比如在哪个楼多放招领点），
   需要知道「哪类物品最容易丢」「哪个时间段发布量高」，看板直接给出答案；
3. **对本项目**：让项目从「信息展示工具」升级为「有数据洞察的平台」，
   这是纯粹加分的设计，也和我们原型里「福大拾光」这个品牌调性一致。

看板包含四张指标卡和两张图表：

| 组件 | 内容 | 为什么有用 |
|---|---|---|
| 指标卡 ×4 | 累计发布 / 成功找回归还 / 正在寻找 / 找回率 | 一眼看清全局 |
| 近 7 天发布趋势（柱状图） | 每日新增数量 | 看活跃度变化，发现「周末丢东西多」之类的规律 |
| 物品类别分布（条形图） | 各类别数量排序 | 提示高发类别（本例中电子产品居多） |

#### 实现思路

**关键决策：不引入图表库（如 ECharts / Chart.js），全部用纯 CSS 绘制。**

原因有两点：
1. **体积与依赖**：ECharts 压缩后还有几百 KB，而我们整个项目才几十 KB。
   为了两张小图表引入一个大库，性价比极低，也违背了「零依赖」的架构决策；
2. **学习成本与可控性**：CSS 画的柱状图高度可控、样式和全站统一、还能直接加 CSS 过渡动画，
   视觉效果并不比图表库差。

技术实现是：**用数据算出每个柱子的高度百分比，直接写入内联 `style` 的 `height`**，
配合 CSS 的 `transition: height .6s` 就有生长动画。

所有统计计算都在 `store.js` 的 `calcStats()` 里完成（纯函数，可单测），
`views.js` 只负责把算好的数字画成 HTML。

#### 关键代码片段

```javascript
// store.js —— 统计计算（纯函数，被单元测试覆盖）
function calcStats(items) {
  var list = Array.isArray(items) ? items : [];
  var stats = { total: list.length, lost: 0, found: 0, closed: 0, open: 0,
                closedRate: 0, byCategory: {}, last7Days: [] };

  list.forEach(function (item) {
    if (item.type === TYPE.LOST) { stats.lost++; }
    if (item.type === TYPE.FOUND) { stats.found++; }
    if (item.status === STATUS.CLOSED) { stats.closed++; } else { stats.open++; }

    var cat = item.category || '其他';
    stats.byCategory[cat] = (stats.byCategory[cat] || 0) + 1;   // 按类别累加
  });

  // 找回率：四舍五入为整数百分比；总数为 0 时直接给 0，避免除零得到 NaN
  stats.closedRate = stats.total === 0
    ? 0
    : Math.round((stats.closed / stats.total) * 100);

  // 近 7 天每日发布量：从 6 天前循环到今天，保证返回的永远是 7 个点
  var today = new Date();
  today.setHours(0, 0, 0, 0);
  for (var i = 6; i >= 0; i--) {
    var day = new Date(today.getTime() - i * 86400000);
    var key = day.getFullYear() + '-' +
      String(day.getMonth() + 1).padStart(2, '0') + '-' +
      String(day.getDate()).padStart(2, '0');
    var count = list.filter(function (item) {
      return String(item.createdAt).slice(0, 10) === key;
    }).length;
    stats.last7Days.push({ date: key, count: count });
  }

  return stats;
}
```

> 💡 **两个细节值得说明**：
> 1. `stats.total === 0 ? 0 : ...` 这个三元判断是必要的。如果没有它，
>    空数据时 `0/0` 会得到 `NaN`，界面上就会显示「找回率 NaN%」。
>    单元测试「用例 39」专门断言了 `Number.isNaN(s.closedRate) === false`。
> 2. 日期循环写成 `for (var i = 6; i >= 0; i--)` 而不是正序，是为了让数组里
>    的日期**从早到晚递增**，这样画出来的柱状图天然就是时间从左到右的顺序。

```javascript
// views.js —— 纯 CSS 柱状图：用数据算出高度
function renderDayChart(days) {
  var max = Math.max.apply(null, days.map(function (d) { return d.count; }).concat([1]));
  return days.map(function (d) {
    // 数量为 0 时给 4px 的最小高度，让用户能看到「这天确实有柱子，只是值为 0」
    var height = d.count === 0 ? 4 : Math.round((d.count / max) * 140) + 8;
    var label = d.date.slice(5).replace('-', '/');
    return [
      '<div class="chart__col">',
      '  <div class="chart__num">' + d.count + '</div>',
      '  <div class="chart__bar" style="height:' + height + 'px"></div>',
      '  <div class="chart__label">' + label + '</div>',
      '</div>'
    ].join('');
  }).join('');
}
```

> 💡 **`.concat([1])` 的作用**：当所有日期的 count 都是 0 时，`max` 会是 0，
> 后面的除法就会变成 `0/0 = NaN`。加一个 `[1]` 保证分母至少是 1。
> 这是写图表代码时非常容易忽略的边界，我们把它记录下来。

**第一步：先搞懂「什么是单元测试」**

| 【工具函数】 | `sortByTimeDesc` `findById` `maskPhone` `daysBetween` `generateId` `todayString` | 9 | 排序正确性、格式校验、唯一性 |
| 【持久化】 | `save` `load` `addItem` `removeItem` | 5 | 读写一致、跨会话、数据损坏降级 |
| 【示例数据】 | `data.js` 的数据质量 | 5 | 类别合法性、内置数据自身可过校验 |

#### 部分关键测试代码

**（1）边界值测试：物品名称长度**

```javascript
it('用例24：物品名称为空或过短（1 个字）应校验失败', function () {
  var d = validData(); d.title = '';
  expect(Store.validateItem(d).valid).to.equal(false);
  expect(Store.validateItem(d).errors).to.have.property('title');

  d.title = '卡';      // 边界：恰好 1 个字符，应该失败
  expect(Store.validateItem(d).valid).to.equal(false);
});

it('用例25：物品名称超过 30 字应校验失败', function () {
  var d = validData();
  d.title = new Array(32).join('测');   // 31 个字符，越过上限
  var r = Store.validateItem(d);
  expect(r.valid).to.equal(false);
  expect(r.errors.title).to.contain('30');
});
```

> **设计说明**：`new Array(32).join('测')` 是一个常用技巧，生成 31 个重复字符。
> 验证的是「上限 +1」这个经典的边界值。

**（2）状态更新的不可变性测试**

```javascript
it('用例18：不应修改原数组（避免视图层数据脏读）', function () {
  var originalStatus = Store.findById(testItems, 'T1').status;
  Store.updateStatus(testItems, 'T1', 'closed');
  expect(Store.findById(testItems, 'T1').status).to.equal(originalStatus);
});
```

> **设计说明**：这条用例保护的是架构约定。如果将来有人把 `updateStatus` 改成原地修改，
> 这条测试会立刻失败，从而拦住可能引发界面 bug 的改动。这是「用测试固化架构决策」。

**（3）除零边界测试**

```javascript
it('用例39：边界 —— 空数据时所有统计应为 0，且不出现除零 NaN', function () {
  var s = Store.calcStats([]);
  expect(s.total).to.equal(0);
  expect(s.closedRate).to.equal(0);
  expect(Number.isNaN(s.closedRate)).to.equal(false);   // 关键断言
  expect(s.last7Days).to.have.lengthOf(7);
});
```

> **设计说明**：`Number.isNaN` 在 Chai 的 `expect` 里不能直接调用（它会尝试把 NaN 当
> 断言目标），所以用原生方法包裹。这条用例的价值在于：如果不写，
> 空数据时界面会显示「找回率 NaN%」，而这个 bug 在数据充足时**永远不会暴露**。

**（4）异常入参的健壮性测试**

```javascript
it('用例8：数据源为空数组或非法入参时，应安全返回空数组', function () {
  expect(Store.searchItems([], { keyword: '任意' })).to.have.lengthOf(0);
  expect(Store.searchItems(null, { keyword: '任意' })).to.have.lengthOf(0);
  expect(Store.searchItems(undefined, {})).to.have.lengthOf(0);
});

it('用例32：边界 —— 传入 null / undefined / 非对象时应安全返回失败', function () {
  expect(Store.validateItem(null).valid).to.equal(false);
  expect(Store.validateItem(undefined).valid).to.equal(false);
  expect(Store.validateItem('字符串').valid).to.equal(false);
});
```

> **设计说明**：传入 `null` 和传入 `'字符串'` 是两种不同性质的错误（空值 vs 类型错误），
> 我们特意都测了。因为 `typeof '字符串' === 'string'`，如果代码里只写
> `if (!data) return ...`，字符串会绕过检查然后 `.title` 得到 `undefined`，
> 后续逻辑可能抛出 `TypeError`。

**（5）unique 性压力测试**

```javascript
it('用例49：generateId 应返回非空且唯一的字符串 ID', function () {
  var ids = {};
  for (var i = 0; i < 500; i++) {
    var id = Store.generateId();
    expect(id).to.be.a('string');
    expect(id.length).to.be.greaterThan(5);
    expect(ids[id]).to.equal(undefined);   // 无重复
    ids[id] = true;
  }
});
```

> **设计说明**：`generateId` 用「时间戳 + 随机串」实现，理论上存在碰撞可能。
> 循环 500 次检测重复，是验证随机部分足够分散的实用做法。
> 500 次在毫秒级完成，不会拖慢测试。

## 8. 遇到的代码模块异常或结对困难及解决方法

### 问题一：一键复制功能在 `file://` 协议下失效

**问题描述**

「一键复制联系方式」在本地开发生成的页面上点击没有任何反应，控制台报错：

```
NotAllowedError: Failed to execute 'writeText' on 'Clipboard':
Document is not focused. / Write permission denied.
```

**做过哪些尝试**

1. 一开始怀疑是按钮事件没绑上，在事件处理里加 `console.log` 确认——事件是触发了的；
2. 检查发现 `navigator.clipboard.writeText()` 返回的 Promise 被 reject，但我们的代码
   当时只写了 `.then()` 没写 `.catch()`，导致错误被静默吞掉，表现成「点击无反应」；
3. 搜索资料后确认根因：**`navigator.clipboard` 属于安全上下文 API，在 `file://` 协议下
   浏览器会拒绝授权**。而本作业恰恰要求「双击 HTML 直接运行」，正好踩中这个坑；
4. 尝试用 `document.execCommand('copy')` 替代——在 `file://` 下可用；
5. 但 `execCommand` 已经标记废弃，未来可能被移除，不能只用它。

**是否解决**：✅ 已解决

**解决方案**：采用**双层降级策略**——优先用现代 `navigator.clipboard`，
`.catch()` 中回退到 `document.execCommand`；如果浏览器连 `clipboard` 都没有，直接走降级。
两种路径都给用户 Toast 反馈。

**有何收获**

- 学到了**「API 可用性 ≠ API 能用」**。`navigator.clipboard` 在现代浏览器里都存在，
  但在 `file://` 下不可用。这提醒我们：**部署形态会影响 API 可用性**，写代码时要考虑
  最终运行环境，而不是只在开发环境测试；
- 学到了 **Promise 一定要 `.catch()`**。这次的「点击无反应」就是因为 unhandled rejection
  被静默忽略，排查时多花了不少时间；
- 加深了对**「渐进增强 / 优雅降级」**的理解——不是所有用户都在最新浏览器和 HTTPS 环境下。

### 问题二：单元测试首次运行有 1 个用例失败——「测试数据设计错误」

**问题描述**

写完 61 个用例后第一次运行，显示：

```
59 passing
1 failing
1) 【搜索】searchItems - 关键词匹配
   用例2：应能匹配详细描述中的文字（关键词「挂饰」）:
   AssertionError: expected [ { id: 'T4', ... } ] to have a length of 2 but got 1
```

**做过哪些尝试**

1. 第一反应是「搜索函数有 bug」，但仔细看数据后发现**是我自己写错了测试数据**：
   T3 的描述是「挂**云朵挂件**」，T4 的描述是「挂蓝色恐龙挂**饰**」——
   「挂件」和「挂饰」虽然都有「挂」字，但**没有「挂饰」这个共同的连续子串**，
   所以搜「挂饰」只能命中 T4；
2. 确认 `searchItems` 本身逻辑正确（子串匹配、多字段合并都对）；
3. 思考如何修改：是改测试数据，还是改断言？

**是否解决**：✅ 已解决

**解决方案**：选择**同时修改数据断言并补充用例**，而不是简单地把 `lengthOf(2)` 改成 `1`：

- 把用例 2 的关键词改为「挂」（能同时命中两条），保留「多条命中」的验证意图；
- **新增用例 2b**，用「恐龙」这个只出现在 T4 描述中的词，专门验证
  「关键词只出现在描述字段、不出现在标题和地点时也能命中」。

这样既修正了错误，又让测试覆盖更全面。

**有何收获**

- **测试代码也是代码，同样需要设计**。这次失败不是产品 bug，而是测试设计缺陷。
  如果当初随手编数据，很可能写成「T3 描述含挂饰、T4 描述含挂件」这种想当然的数据，
  然后为了让测试通过而把断言改成 `lengthOf(1)`，**那就把测试的意义彻底丢掉了**；
- 学会了区分两种情况：「产品代码错了」vs「测试写错了」。前者要改源码，
  后者要改测试。**绝不能为了让测试通过而弱化断言**，那等于自欺欺人；
- 体会到「失败信息足够详细」的重要性。因为断言里写了中文描述、`.with.lengthOf(2)`
  也给出了期望值，一眼就能定位问题，省去了大量排查时间。

### 结对困难：对「界面美观」标准的理解不一致

**问题描述**

我个人认为功能性最重要，界面「能用就行」；但是姜思源希望多做视觉效果（渐变、阴影、动效）。
两人在样式代码上产生了分歧：我 觉得 姜花了太多时间在「不重要的地方」，
但她 觉得 我 的界面「太朴素，作业评分里美观性占 10 分」。

**做过哪些尝试**

1. 一起重新读了一遍评分规则，发现**美观性确实占 10 分**，而且规则里明确写了
   「朴素不加修饰取最低分 5 分」——说明作业是明确鼓励做视觉打磨的；
2. 也发现 我 的担忧有道理：如果时间都花在美化上，测试和文档就会赶不上 deadline；
3. 于是我们做了**时间分配的约定**。

**是否解决**：✅ 已解决

**解决方案**

- 明确**优先级**：先把「发布—浏览/搜索—详情—联系—更新状态」这条主流程跑通（对应功能性 15 分），
  确认功能完备后，再投入时间做视觉；
- **把美观工作集中在 `style.css`**：因为 CSS 与逻辑完全解耦（这正是我们分层架构的收益），
  所以美化过程不会引入功能 bug，风险可控；
- 我 负责跑一遍 `npm test` 确认 61 个用例仍然全绿，作为「美化没有破坏功能」的守门人。

**有何收获**

- **分歧的解法是回到评分规则，用「共同目标」而非「个人偏好」来做决策**。
  与其争论「要不要美化」，不如问「评分规则怎么说的，剩下的时间够不够」；
- 体会到了**好的架构能让协作更顺畅**。如果 CSS 和 JS 混在一起，
  姜思源 改样式的过程很可能改坏 我 的逻辑，分歧会升级成技术冲突。
  正因为我们把样式隔离在 `style.css`、逻辑集中在 `store.js`，
  两人的工作才能并行推进、互不干扰；
- 学会了**给非功能性需求设定时间和范围的边界**，而不是简单地争论「要不要做」。

### 9.3 我们两个人的共同收获

最大的收获是**理解了「结对编程」不是「分工干活」**。

作业初期我们其实是「各做各的」——我 写逻辑，姜思源 写界面，最后合并时才发现接口对不上：
我 的 `searchItems` 返回的是数组，但 姜思源 的渲染函数期望的是一个带 `total` 字段的对象。
这次返工让我们意识到，**结对的核心价值在于「实时的设计对齐」**，
而不是把工作量对半分。

后来我们调整了方式：**每个模块开工前先用 10 分钟口头对齐接口**
（函数名、参数、返回值结构），对接成本大幅降低。
这 10 分钟花得非常值——它避免了后面几个小时的返工。

## 11. 最后的话

这次作业我们最大的感受是：**「做一个能跑的程序」和「做一个别人能跑起来的程序」
之间隔着很多细节**。

比如「一键复制」这个看起来 10 行代码就能搞定的功能，因为要适配 `file://` 协议
而不得不写降级方案；再比如「零依赖」这个决定，意味着所有第三方库都要下载到本地、
所有图表都要手写 CSS。但正是这些选择，让助教双击 `index.html` 就能看到完整效果，
让测试环节没有任何环境障碍。

如果重来一次，我们会在**项目开始时就用 10 分钟做技术预研**（尤其是
「浏览器在要求的运行环境下，哪些 API 不可用」），而不是等到踩坑再补救。
